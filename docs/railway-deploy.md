# Railway deployment (marketplace-indexing Nexus)

A standalone Nexus instance that indexes the **official staging homeserver** so the
deployed pubky-app marketplace gets catalog discovery (`/v0/stream/listings`,
`/v0/shop/{seller_id}`, `/v0/listing/{seller_id}/{listing_id}`).

## Topology

Railway project **`pubky-marketplace-nexus`** (separate from
`pubky-marketplace-staging`, which hosts payment-rail services), environment
`production`, three services on the project's private network:

| Service  | Source                                        | Volume                    | Notes |
|----------|-----------------------------------------------|---------------------------|-------|
| `neo4j`  | image `neo4j:5.26.20-community`               | `neo4j-volume` → `/data`  | Auth via `NEO4J_AUTH=neo4j/<password>`; listens on `::` (Railway private networking is IPv6-only); heap 1G / pagecache 512M; telemetry off |
| `Redis`  | Railway Redis template (redis-stack)          | `redis-volume` → `/data`  | Password auto-generated by the template; exposes `REDIS_URL` |
| `nexusd` | this repo, branch `feat/marketplace-indexing` | `nexusd-volume` → `/data` | Built with `Dockerfile.railway` (see `railway.toml`); runs API + watcher in one process |

Private wiring (no public exposure of the databases):

- `nexusd → neo4j`: `bolt://neo4j.railway.internal:7687`
- `nexusd → Redis`: `redis://default:<password>@redis.railway.internal:6379`
  (referenced as `${{Redis.REDIS_URL}}`)

Public domain (API only): **https://nexusd-production-7108.up.railway.app**

## nexusd configuration

`nexusd` reads a `config.toml` from `--config-dir`. On Railway,
`entrypoint-railway.sh` generates `/data/config.toml` from environment
variables at boot, then runs `nexusd --config-dir /data` (API + watcher).

Variables set on the `nexusd` service:

| Variable | Value | Purpose |
|----------|-------|---------|
| `NEXUS_HOMESERVER` | `ufibwbmed6jeq9k4p583go95wofakh9fwpp4k734trq79pd9u1uy` | Official staging homeserver (https://homeserver.staging.pubky.app) |
| `NEXUS_NEO4J_URI` | `bolt://neo4j.railway.internal:7687` | Graph DB |
| `NEXUS_NEO4J_PASSWORD` | (secret) | Matches the `neo4j` service's `NEO4J_AUTH` |
| `NEXUS_REDIS_URL` | `${{Redis.REDIS_URL}}` | Cache/index |
| `NEXUS_TESTNET` | `false` | Staging homeserver publishes on the mainnet DHT |
| `PORT` | `8080` | API bind port (entrypoint uses it for `public_addr`) |
| `NEXUS_EVENTS_LIMIT` | default `1000` | Events fetched per watcher poll |
| `NEXUS_WATCHER_SLEEP` | default `500` (ms) | Sleep between watcher polls |
| `NEXUS_MODERATION_ID` | no safe default | Public key (pubky) of pubky.app's production moderator account, the one account whose moderation tags are trusted. Set it explicitly: unset falls back to a built-in key that is not verified as pubky.app's production moderator, and the entrypoint warns |
| `NEXUS_MODERATED_TAGS` | default `moderated` | Comma-separated labels that, placed by the moderator, take the tagged post, user, file or listing out of the index (a tagged user takes their shop and listings with them). Moderation is on by default with the current entrypoint: when
`NEXUS_MODERATED_TAGS` is unset it defaults to `moderated`, so set
`NEXUS_MODERATION_ID` to the moderator key in the same change that deploys the
image. Both variables are declared with `preserve()` in `.railway/railway.ts`,
so an IaC apply keeps the values set in Railway.

### Moderation: launched setting

The Shop index applies the same moderation as pubky.app: content and users that
pubky.app's moderator account tags are removed from the index.

| Setting | Railway variable (generated `config.toml` key under `[watcher]`) | Launched value | Where the value comes from |
|---|---|---|---|
| Moderator key | `NEXUS_MODERATION_ID` (`moderation_id`) | pubky.app's production moderator public key | The operators of pubky.app's production Nexus hold it in that deployment's watcher config (`moderation_id`). It is not in any public repository: upstream `pubky-nexus` ships only a test key (`uo7jgkykft4885n8cruizwy6khw71mnu5pq3ay9i8pw1ymcn85ko`, marked "test user key, overridden by config.toml value"), and this entrypoint's built-in fallback (`51y9w1skwcryb3iq4sia3x49qwpgstc5feo5tqon65gid7o99khy`) is an older upstream constant that was never confirmed as the live key. |
| Moderation labels | `NEXUS_MODERATED_TAGS` (`moderated_tags`) | pubky.app's production label list, comma separated | Same source (`moderated_tags` in that config). Upstream's defaults, to compare against and not to copy blindly: `hatespeech`, `harassement` (sic), `terrorism`, `violence`, `illegal_activities`, `il_adult_nu_sex_act`. This fork also moderates `moderated`, the label its proof-listing cleanup uses; keep it in the list only while the moderator account uses it. |

Who sets it: whoever operates the Shop index deployment (the Railway service,
or the GCP deployment's `[watcher]` config), copying the two values from the
pubky.app production Nexus configuration. Nothing in this repository can supply
them. Do not put a personal or throwaway key here: a moderator tag from any
other key is an ordinary community tag.

After a deploy, read the generated config in the service log
("Generated config (credentials redacted)"): `moderation_id` must equal
pubky.app's production moderator key and `moderated_tags` its production label
list, and the boot log must not contain the `NEXUS_MODERATION_ID is not set`
warning. The moderator account must be on a homeserver this Nexus watches, or
its tags are never seen (see the next section).

What the moderator's tags do on this index:

| Tag on | Effect |
|---|---|
| a marketplace listing | the listing leaves the graph, the details cache and every stream; stays out across a reindex (`ModeratedListing` marker) |
| a user's profile | the user, their shop and every listing leave the index; the shop and listings stay out across a reindex, and a listing or shop the seller publishes later is not indexed (`ModeratedUser` marker) |
| a post, file or tag | removed, as on pubky.app |

Removing the moderator's tag restores what it hid, from the seller's
homeserver. `GET /v0/listing/{seller_id}/{listing_id}/moderation` reports
whether a listing is moderated, through the listing's own marker or its
seller's, for a listing the index holds or not; the transaction service reads
it before it sells, takes a bid on, or takes an offer on a listing.

### Index discovery: launched setting

| Setting | Launched value | Where |
|---|---|---|
| Default homeserver | exactly one: the value of `NEXUS_HOMESERVER` | `homeserver` in the generated config |
| Discovery limit | `50` | `monitored_homeservers_limit = 50`, fixed in `entrypoint-railway.sh` (no variable) |

The watcher always polls the default homeserver. It adds other homeservers it
discovers through follows, tags, mentions and reviews, up to the discovery limit
of 50 monitored homeservers in total.

### Homeserver watching: no credentials, full history replay

The watcher polls the homeserver's **public** event stream
(`https://<homeserver_pubky>/events/?cursor=…&limit=…`, resolved via pkarr) —
no credentials or session are needed. The event stream has **no path filter**:
a new Nexus starts at cursor `0000000000000` and must replay the homeserver's
entire event history (profiles, posts, follows, files, … *and* marketplace
records). It cannot run scoped to marketplace paths only; listing indexing
also depends on the seller's user profile being indexed first, so the full
replay is what makes marketplace rows land correctly. The cursor is persisted
in Redis, so restarts resume where they left off.

Observed on first deploy (2026-08-21): the staging homeserver history was
~115,000 events, and the watcher processed roughly 100–160 events/minute from
Railway (each PUT costs at least one content fetch from the homeserver), i.e.
a full cold replay takes on the order of half a day. Progress can be tracked
with:

```bash
railway logs --service nexusd | grep "cursor for the next request"
```

## How to redeploy

The Railway account has no GitHub integration installed, so the service is
deployed by uploading the working tree with the CLI (uploads honor
`.railwayignore`):

```bash
cd pubky-nexus
git checkout feat/marketplace-indexing && git pull
railway link   # once: project pubky-marketplace-nexus
railway up --service nexusd --detach
```

If the Railway GitHub app is ever installed for `BitcoinErrorLog`, connect the
service to `BitcoinErrorLog/pubky-nexus` @ `feat/marketplace-indexing` in the
dashboard so pushes redeploy automatically; `railway.toml` already points the
builder at `Dockerfile.railway`.

## Running the backfill migrations on Railway

Two one-shot migrations exist (see the runbook in `README.md`):

- `ListingAuctionTermsReindex1787256279` re-reads auction listings that
  predate the auction-term fields.
- `ReviewBackfill1787905961` discovers and indexes marketplace reviews
  published BEFORE the deployed watcher's replay cursor, by LISTing every
  indexed user's reviews directory on their homeserver and running the
  normal ingest (attestation verification and reputation recompute
  included).

On Railway, run them inside the `nexusd` container so they reach the private
databases:

```bash
railway ssh --service nexusd
# inside the container — the migration reads ~/.pubky-nexus/migrations/config.toml,
# created with defaults on first run; point it at the Railway databases:
mkdir -p ~/.pubky-nexus/migrations
cat > ~/.pubky-nexus/migrations/config.toml <<EOF
name = "nexusd.migration"
backfill_ready = ["ListingAuctionTermsReindex1787256279", "ReviewBackfill1787905961"]
testnet = false
testnet_host = "localhost"

[stack]
log_level = "info"
files_path = "/data/static/files"

[stack.db]
redis = "$NEXUS_REDIS_URL"

[stack.db.neo4j]
uri = "$NEXUS_NEO4J_URI"
password = "$NEXUS_NEO4J_PASSWORD"
EOF
nexusd db migration run
```

Both migrations are idempotent. The review backfill treats a missing review
directory or record (homeserver 404) as gone. If a user's homeserver cannot be
reached while its review directory is listed, that user is logged and counted
as `unreachable` but skipped so one offline homeserver cannot permanently block
this migration or the migrations after it. Record-level fetch, parse, and
ingest failures still fail the migration and are retried on the next run;
already-indexed reviews are skipped. The watcher does not need to be stopped.
